## Introduction to Events and Listeners

### Universal Programming Concept
**Key Insight**: Regardless of programming language or paradigm, programs must handle situations where they **wait for events to happen**.

### Two General Approaches

#### 1. Polling for Events
```
while (event hasn't happened) {
    keep checking...
}
```
**Characteristics**:
- ✅ **Easy to implement**
- ❌ **Wasteful of resources** (continuous checking)
- ❌ **Poor performance** (busy waiting)

#### 2. Event-Driven Programming
**Contract with Operating System**: 
"I'll release my resources, providing you notify me when my event happens"

**Characteristics**:
- ❌ **More complex to write**
- ✅ **Much better resource usage**
- ✅ **Better performance** (reactive approach)

## Java Event Model - Delegation Model

### Historical Context
Java events (from **Java 1.1 onwards**) use the **delegation model**.

### Key Principle
**Events are only distributed to objects that register to listen for them**

### Three Core Components

#### 1. Source
**Definition**: Object that **generates an event**

**Characteristics**:
- Event generation occurs in response to **internal state changes**
- Must **register listeners** for event distribution
- **Cannot notify** unregistered listeners

#### 2. Listener  
**Definition**: Object that is **notified when events occur**

**Requirements**:
1. Must **register** with event source
2. Must **implement methods** to handle notifications

#### 3. Event
**Definition**: Object containing **information about state change** in source

**Purpose**: Carries data about what happened and where

### Event Flow Diagram
```
Source Object → State Change → Event Object → Registered Listener → Event Handler Method
```

## Java Event Framework Components

### Core Framework Elements
The Java event framework consists of:
- **Two concrete classes**
- **One abstract class** 
- **One interface**
- **Naming conventions**

### Most Important Elements

#### 1. java.util.EventObject (Abstract Class)
- **Base class** for all event objects
- **Minimum requirement**: Record source object

#### 2. java.util.EventListener (Interface)
- **Marker interface** for all event listeners
- **No methods** - just identification

## Listeners in Detail

### Listener Interface Structure
**Event listener** = Different method for each event type

#### Event Notification Categories
Events are **grouped by category**:
- **Button events** → `ActionEvent`
- **Key events** → `KeyEvent` 
- **Mouse events** → `MouseEvent`

#### Naming Convention
**Event listener interfaces** named: `EventCategoryNameListener`

**Examples**:
- `ActionListener`
- `KeyListener`
- `MouseListener`

#### Implementation Requirement
```java
// To receive events, class must implement listener interface
public class MyClass implements ActionListener {
    // Must implement required methods
}
```

### Event Listener Relationships

#### Typical Pattern: One-to-One
- `ActionListener` ↔ `ActionEvent`
- `KeyListener` ↔ `KeyEvent`

#### Multiple Methods per Listener
Some listeners handle **multiple related events**:

```java
interface KeyListener extends EventListener {
    public void keyPressed(KeyEvent e);
    public void keyReleased(KeyEvent e); 
    public void keyTyped(KeyEvent e);
}
```

#### Method Signature Pattern
```java
public void specificEvent(EventCategoryNameEvent e)
```

**Examples**:
```java
public void actionPerformed(ActionEvent e)
public void keyPressed(KeyEvent e)
public void mouseClicked(MouseEvent e)
```

## Events in Detail

### Event Object Requirements

#### State Capture
**All event-related state** must be captured when event occurs

#### Class Hierarchy
Event class **must extend** `java.util.EventObject`

#### Minimum Requirement
Must record **source object** that generated the event

#### Naming Convention
Event classes named: `EventCategoryNameEvent`

**Examples**:
- `ActionEvent`
- `KeyEvent` 
- `ScannedRobotEvent`

### Event Object Contents
Typical event objects contain:
- **Source reference** (required)
- **Timestamp** (when event occurred)
- **Event-specific data** (coordinates, key codes, etc.)

## Sources in Detail

### Pre-existing Sources
Many sources come **built-in**:
- **GUI components** (buttons, text fields)
- **Enterprise JavaBeans**
- **System components**

### Custom Source Creation
Framework allows **bespoke source classes**

#### Registration Method Requirements
Source classes must provide **registration methods** for each listener type:

**Method Signature Pattern**:
```java
public void addEventCategoryListener(EventCategoryListener listener)
```

**Examples**:
```java
public void addActionListener(ActionListener listener)
public void addKeyListener(KeyListener listener)
public void addMouseListener(MouseListener listener)
```

#### Implementation Pattern
```java
public class CustomSource {
    private List<ActionListener> listeners = new ArrayList<>();
    
    // Registration method
    public void addActionListener(ActionListener listener) {
        listeners.add(listener);
    }
    
    // Event firing method
    private void fireActionEvent() {
        ActionEvent event = new ActionEvent(this, ActionEvent.ACTION_PERFORMED, "command");
        for (ActionListener listener : listeners) {
            listener.actionPerformed(event);
        }
    }
}
```

## Practical Example: Beeper Class

### Complete Implementation
```java
public class Beeper extends JPanel implements ActionListener {
    JButton button; 
    
    public Beeper() {
        super(new BorderLayout());
        
        // Create source (button)
        button = new JButton("Click Me"); 
        button.setPreferredSize(new Dimension(200, 80)); 
        add(button, BorderLayout.CENTER); 
        
        // Register this object as listener
        button.addActionListener(this); 
    }
    
    // Event handler method
    public void actionPerformed(ActionEvent e) { 
        Toolkit.getDefaultToolkit().beep(); 
    } 
}
```

### Key Elements Demonstrated

1. **Source**: `JButton button`
2. **Listener**: `Beeper` class (implements `ActionListener`)
3. **Event**: `ActionEvent e`
4. **Registration**: `button.addActionListener(this)`
5. **Handler**: `actionPerformed()` method

### Event Flow in Beeper Example
1. **User clicks** button
2. **Button generates** `ActionEvent`
3. **Event distributed** to registered listeners
4. **Beeper's** `actionPerformed()` method called
5. **System beep** sound plays

## Framework Flexibility

### Component Registration
- **One source** → **Multiple listeners**
- **One listener** → **Multiple sources**
- **Dynamic registration/unregistration**

### Event Filtering
- Listeners only receive **registered event types**
- **Type safety** through interface implementation
- **Compile-time checking** of handler methods

## Best Practices

### Listener Implementation
1. **Implement specific interfaces** only for needed events
2. **Keep handler methods lightweight** (avoid blocking operations)
3. **Handle exceptions** gracefully in event handlers
4. **Unregister listeners** when no longer needed (prevent memory leaks)

### Source Design
1. **Provide clear registration methods**
2. **Document event firing conditions** 
3. **Thread safety** for listener lists
4. **Null checks** for listener operations

## Key Takeaways

### Event-Driven Programming Benefits
1. **Resource efficiency** - no continuous polling
2. **Responsive applications** - react when needed
3. **Scalable architecture** - handles multiple event sources
4. **Separation of concerns** - sources don't know about listeners

### Java Event Model Strengths
1. **Type safety** through interfaces
2. **Flexible registration** system
3. **Standardized naming** conventions
4. **Built-in GUI integration**

### When to Use Events
- **User interfaces** (button clicks, key presses)
- **Asynchronous operations** (network responses, file operations)
- **System monitoring** (file changes, system status)
- **Inter-component communication** in complex applications

- **Registration methods** for source-listener binding
